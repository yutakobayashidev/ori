# AIインボックスを圧倒されずに扱うための時間モデル

設計・実装記録（2026-10-09）。AI見積もり、自動分類、集中画面、実績ログ、MCP時間更新を実装。
カレンダー連携・作業枠は今回の対象外。以下のカレンダー節は将来設計として保持する。

## 目的

AIがメッセージや文脈から次々にActivityを追加する。本人に全件の判断・処理を
要求せず、「今ならこれに着手できそう」と選べるようにする。
推定時間はこの判断の補助であり、全タスクを予定表へ詰めるためのノルマではない。

Homeの `Start here` / `If there’s room` はAIの推奨区分をそのまま使う。
Activityを受け取るたびにHomeへ反映し、本人に日次候補を選ばせない。
未完了件数や未処理時間の合計を常時強調しない。全件の見積もり・期限・予定時刻の
入力は求めない。AI由来のActivityには控えめな印を付け、本人が作った項目と見分ける。

## 導入前の実装

- SQLiteの共通Activityで返信と雑用を保存。AIの `proposal`、本人の
  `userOverrides`、合成した `effective`、`userState` を持つ。
- `focus` / `optional` は表示の区分。日付や所要時間を持つ日次計画ではない。
- 見積もり・実績ログ・残り時間・作業予定日時の構造化フィールドはない。
- `inProgress` は状態。開始から経過した時間やAI executionの稼働時間は本人の
  作業実績ではない。
- Google Calendar接続・永続化されたカレンダービューはない。古い
  conversation-detailのcalendar holdはモック。

## Tiimoから参考にする点

[Tasks & to-dos](https://www.tiimoapp.com/faq/manage-tasks) は未配置のTo-doと、
Todayの時刻付き/Anytimeタスクを区別する。
[Focus timer](https://www.tiimoapp.com/faq/focus-timer) はAnytimeを任意のタイミングで
開始できる。[Visual planning](https://www.tiimoapp.com/product/visual-planning) は
所要時間の目安、並べ替え、予定変更を支援する。

これは公開された挙動の調査であり、Tiimo内部のDBスキーマを確認したものではない。
このアプリではAIが大量に収集するため、Start here / If there’s roomの自動分類で
本人の仕分け負担を減らす。
Tiimoの時刻に連動したタイマー自動開始は採用せず、本人が始めたときだけ計測する。

## データを分ける

| レコード                      | 役割                                                   |
| ----------------------------- | ------------------------------------------------------ |
| Activity                      | 何をするか。返信も雑用も同じインボックス。既存IDを維持 |
| Activityの時間見積もり        | どの程度の作業か。任意の目安と根拠                     |
| Recommendation                | `Start here` / `If there’s room` の自動分類と理由      |
| FocusSession                  | 本人が今取り組む1件と、今回の集中時間・計測状態        |
| WorkLog                       | 実際に本人が取り組んだ時間。入力・計測は任意           |
| Calendar event / 任意の作業枠 | 時刻を持つ予定。候補選定や作業実績とは別               |

### Activityの時間情報

AI提案の `timeEstimate.estimatedMinutes` と本人overrideの `estimatedMinutes` に正の整数を保存する。
初期表示は「約15分」程度。未見積は未見積として扱い、0分にしない。
通常はDotsがActivityを作る際に、元の会話・返信案・次の行動から作業時間の
デフォルト値を埋める。本人へ見積もり入力や承認を要求しない。
5分・10分・15分・30分などの粗い目安を使い、細かい精度を装わない。
情報が少なくても合理的な仮定が置けるなら暫定値と根拠を付ける。
作業範囲そのものが不明な場合だけ未見積を許容し、登録や着手は妨げない。
本人が修正した値はAI再提案で上書きしない。
AIの値には `timeEstimate.reason` とサーバー側の更新時刻を持たせ、詳細で確認できるようにする。
見積もりの対象は本人の能動的な作業。相手からの返答待ちやAI実行待ちは含めない。

`remainingMinutes?: nonnegative integer` は「あとどのくらいか」という別の見積もり。
実績が増えたから自動でタスクを完了したり、残りを負にしたりしない。
明示的な残り見積もりがあればそれを優先し、なければ初期見積もりを目安に使う。
残りの更新は本人の操作、または新しい会話文脈を読んだDotsの根拠付き提案。
通常の更新担当はDotsとし、進捗・返信・作業範囲の変化を根拠に残りを再見積もりする。
本人による調整は任意。毎回「あと何分か」を回答させない。
保存された残り見積もりは実績だけで書き換えない。表示上の予測は後述の基準点から計算する。

長いタスクも排除せず、必要なら「まず資料を開く・約5分」のような着手案を提示する。
この5分とタスク全体の残り時間は混ぜない。初期は `nextAction` の説明として扱い、
段階・サブタスクの独立モデルは実際に必要になってから追加する。

### Recommendation（自動分類）

AIの `recommendation.section` がHomeの表示区分を決める。本人のsection overrideが
あればそちらを優先する。新着を隠さず、自動でStart here / If there’s roomへ分類する。
本人がLaterまたはNot neededを選んだActivityは通常のHome一覧から外し、必要なら
後から戻せる。手動追加のタスクは作成時に選んだsectionへ直接入る。

DaySelectionの永続化とrepositoryは残っているが、MCPツール一覧からは外し、Homeの日々のフローでも使わない。
自動分類を置き換える日次確認ステップや選択上限を再導入しない。

### WorkLog（実績）

`id`, `activityId`, `durationSeconds`, `occurredOn`, `source: manual | timer`,
任意の `startedAt`, `endedAt`, `note`。ログ合計をactualMinutesとして返す。
未記録はnull。計測なしで完了できる。会話やカレンダーの時間から実績を捏造しない。
入力誤りはログID指定で訂正できる。

最初の作業記録時点の見積もりを比較基準として保存し、後の再見積もりで消さない。
比較は「次は少し余裕を見よう」のために詳細画面で使う。毎回の超過警告・成績表示・
未入力の催促はしない。Focusタイマーを使わずに作業してもよい。

### FocusSessionと集中画面

[Tiimoの集中画面](https://www.tiimoapp.com/ja/product/focus) のように、選んだ1件が
画面の主役になる。大きな円形の残り時間表示、タスク名、次の行動を配置する。
集中中はインボックスの件数や新着候補を前面に出さない。返信案や元メッセージは
必要なときに同じ画面から開ける。新着によって集中対象を切り替えない。

時間は以下を区別する。

- 今回の集中時間：本人が選ぶ作業の区切り。例えば全体40分でも今回は15分。
  円形表示とカウントダウンはこちらを表す。
- 完了までの作業量：Activityの残り見積もり。「残り作業の目安 約40分」と小さく表示。
- 推定完了時刻：「続ければ15:40ごろ」。締切や約束ではなく、連続して取り組む場合の
  見込み。集中タイマーの終了時刻とは別に表示する。

開始時の集中時間にも既定値を入れ、本人は時間を入力せず開始できる。
初期案は表示上の残り予測と25分の小さい方（分単位に切り上げ）、未見積または予測0なら15分とする。
これは集中する区切りのUI既定値であり、AIの作業時間見積もりには代入しない。
本人は開始前や途中で自由に変えられる。

`FocusSession` は `id`, `activityId`, `budgetSeconds`,
`state: running | paused | ended`, `startedAt`, `runningSince?`,
`elapsedActiveSeconds`, `endedAt?`, `timeZone` を持つ。本人ごとに実行中は1件。
timeZoneは開始時の端末のIANAタイムゾーン。実績の日付もこのゾーンの開始日を使う。
経過時間は時刻との差分で計算し、毎秒DBへ書き込まない。休止時間は実績に含めない。
終了時にsession IDにひも付いたWorkLogを一度だけ確定し、二重計上を防ぐ。

推定完了時刻は独立した確定日時としてActivityに保存しない。再見積もり時に
残り見積もりとその時点の累積作業時間をActivity単位で記録し、そこを起点とした見込みを
計算する。休止中は「再開後 約○分」の表示にする。これは表示上の予測であり、
Activityの残り見積もりや進捗を経過時間だけで書き換えない。
見積もりがなければ時刻を捏造せず、当初の見込みを過ぎた場合も赤い超過表示にしない。
「見積もりを調整」から任意で更新できる。予定や待ち時間を考慮しない初期実装では、
必ず「続ければ」という条件を添え、実際の作業速度を測ったような表現をしない。

操作は一時停止/再開、5分追加、完了、今日はここまでを中心にする。
カウントダウンが0になってもActivityを自動完了させない。継続・区切るを選べる。
集中画面を閉じることと計測を止めることも分け、継続中は小さなタイマーを残す。
Dotsの根拠付き更新で対象が完了した場合は計測を終了し、静かに完了を伝える。

## 今日の候補をどう選ぶか

締切や実際の約束、文脈、本人の選択を優先し、所要時間は補助として使う。
「15分くらいなら」という本人の指定があればAIはその文脈を使って分類する。
未見積や長いタスクを永久に隠さず、細切れの雑用だけを推薦し続けない。
全件をStart hereへ入れたり、カレンダーの空き時間を埋め尽くしたりせず、
`recommendation.reason` に短い分類理由を添える。

## カレンダービュー

同じActivityを別の表示で見る。全件の開始時刻を必須にしない。

- 時間軸にはGoogle Calendarの会議など、時刻のある予定を表示。
- 時刻未指定の今日の候補はStart here / If there’s roomとして独立して表示。
- 必要なタスクだけ任意で時刻に置く。作業枠はアプリ内計画であり、外部への予約ではない。
- 時刻を過ぎても後続タスクを自動で赤くしたり、未着手を期限切れへ変えたりしない。
- 見積時間はカードの小さなラベル。予定枠を置いた場合は長さの初期値に使える。
- 実際の締切と、本人が仮に置いた作業時刻は別フィールドにする。
- 外部予定の同期に失敗した時間帯を「空き」と断定しない。

Googleの予定はGoogleを正本とする。接続と期間取得が必要で、Dots側の接続があっても
アプリのカレンダービューから自動で使えるわけではない。初期は読み取り連携とする。

## MCP / APIと導入順

既存のrequestId、expectedRevision、本人override保護、共通サービスを継続。
`publish_activities` のツール説明とDotsへの指示では、通常は時間見積もりも
一緒に提案することを既定とする。サーバーが固定値をAI推論として補完しない。
`publish_activities` の `recommendation.section` がHomeの自動分類に使われる。
`get_activity_context` は分類・時間情報を返す。DaySelection APIは互換のため残るが、
通常のタスク追加や日次運用でDotsに呼ばせない。時間更新は既存のorigin付きイベントへ
接続し、AI自身の更新に無限反応しない。

1. AI見積もりの保存・小さな表示、集中画面とFocusSession、実績・残り更新を一通り接続。
2. Google予定の読み取りと柔軟な日ビュー。日時なし候補を維持する。
3. 必要なら任意作業枠・週表示・実績比較の振り返り。

## カレンダーを確認する返信案

合意済みの方針：日程調整ではGoogle Calendarを確認して、具体的な候補日・曜日・
開始終了時刻を返信案に含める。所要時間やタイムゾーンが不明なら確定しない。
確認できなかった空きを断定せず、下書きだけで予約・送信を行わない。

接続権限を持つDots側で照会し、MCPの返信案ツールにも同じ指針を添える。
このルールとカレンダー接続は、現時点ではまだ実装していない。

## 実装契約

以下は時間・集中機能の実装契約。カレンダーは含めない。
初期リリースは単一ownerの現行workspaceを前提とする。

### 見積もりの保存と読み取り

Activityの `proposal.timeEstimate` に `{ estimatedMinutes, reason }` を追加する。
数値は正の整数、reasonは1〜2000文字。どちらか片方だけの指定は認めない。
既存Activityと手入力の作成は値なしを許容する。Dotsが新規作成する通常経路では
必ず見積もりを添える。publishは既存どおり提案全体の置換なので、更新時も値を保持する。
AI見積もりに固定値を埋めるサーバー処理や、別の推論サーバーは追加しない。

進捗に伴う残り見積もりはproposalの全置換から独立した `activity_time` に保存する。
Activity IDを主キーとし、次の情報を持つ。全体見積もりの更新時刻もここに保存する。

- AIのremainingEstimate、本人のremainingOverride。それぞれ
  `{ minutes, reason, updatedAt, activeSecondsAtEstimate }`。
  minutesは0以上の整数。本人のreasonだけ省略可能。時刻と積算値はサーバーが設定。
- 本人の全体見積もりは既存userOverridesの `estimatedMinutes` に保存。
  `resetOverrides` へ時間の2項目を追加し、本人だけがAIへ委ね直せる。
- `initialEstimatedMinutes`：初回集中開始または最初の手入力実績時点の全体見積もり。
  未見積ならnullを維持。後日の値で過去の予測を作らない。

本人の残りoverrideをAIは上書きできない。AIの最新提案は裏で保持し、解除時には
その提案の作成時点からの経過を使う。全体のowner overrideと残りのoverrideは独立。
全体見積もりの編集だけでは、既にある残り見積もりは変更しない。

読み取りは既存Activityに `time` を追加し、全体・残りの値、出所、根拠、更新時刻、
実績秒数、初回比較値を返す。未見積はnull、未記録の実績もnull。
owner値とAI値を混ぜて「AIの見積もり」と表示しない。残りoverrideは数値・根拠・基準点を
原子的に選び、既存の浅いmergeへ数値だけ追加しない。

### 残り表示と推定完了時刻の計算

残り見積もりの事実と、時計を使った表示上の予測を分ける。再開時に毎回元の40分へ
戻らないよう、見積もり時点の累積作業秒数をActivity単位で持つ。
セッションはこのActivity単位の基準を参照し、二重に正本を持たない。

```text
activeSeconds = 確定WorkLogの合計 + 未終了セッションの稼働秒数
workedSinceEstimate = max(0, activeSeconds - activeSecondsAtEstimate)
projectedRemaining = max(0, minutes * 60 - workedSinceEstimate)
連続作業の完了見込み = serverNow + projectedRemaining
```

残りの再見積もりがなければ、全体の見積もりと積算0を初期基準にする。
この減算結果は `remainingEstimate` へ保存しない。時間を使ったことは完了の証拠ではない。
UIは「残りの目安 約○分」と表示し、詳細にAIの元の見積もり・時点を表示する。
分表示は切り上げ、時計は5分程度へ丸めて「ごろ」を添える。
0に達して未完了なら「見込み時間に到達」としてETAを隠し、完了時刻を毎秒先延ばししない。
AIの再見積もりが届かなくても作業の継続・終了は可能。

例：15:00にAIの40分見積もりで開始。15:15に区切ると予測残り25分。
15:30に再開すると「続ければ15:55ごろ」。元の40分から再開しない。
その後Dotsが「資料確認が済み、あと10分」と更新すれば、その時点の実績を新しい基準にする。
集中タイマーの＋5分はこの見積もりを変えない。
手入力実績の訂正時は積算を再計算する。見積もり以前のログ訂正分は基準値にも同量反映する。
見積もり時点をまたぐ集中ログの訂正は、見積もり前後の作業割合に応じて配分する。
この割合は0分へ訂正しても保持し、後で元へ戻した際に二重減算を起こさない。
この基準点調整は同じトランザクションで処理する。

### 集中の状態遷移と実績

| 操作                                               | FocusSession                      | Activity                                                                   |
| -------------------------------------------------- | --------------------------------- | -------------------------------------------------------------------------- |
| 開始                                               | runningを作成                     | availableのみinProgressへ。waiting等は開始を拒否し、状態の見直しを先に行う |
| 一時停止                                           | 稼働秒を確定してpaused            | 変更なし                                                                   |
| 再開                                               | pausedからrunning                 | 終了済みActivityでは拒否                                                   |
| ＋5分                                              | budgetSecondsに300加算            | 見積もり・状態は変更なし                                                   |
| 今日はここまで                                     | ended、実績確定                   | inProgressのまま。今日の候補除外は別操作                                   |
| 完了                                               | ended、実績確定                   | completed                                                                  |
| 外部からcompleted/dismissed/waiting/deferredへ変更 | 未終了セッションをended、実績確定 | 指定状態                                                                   |
| 画面を閉じる                                       | 変更なし                          | 変更なし                                                                   |

未終了セッションはpausedを含めworkspaceに1件まで。別タスクを始める場合は
「現在の集中を区切って開始」の明示操作を用意し、終了と開始を同一トランザクションにする。
開始時はavailable/inProgressのみ許可。再開も同じ条件を検証する。

実績の正本は秒単位の `durationSeconds` とし、分への変換は合計後の表示時に行う。
WorkLogにnullableの `focusSessionId`（unique）を持たせ、終了時の二重計上を防ぐ。
未終了セッションの稼働分は読み取り時だけ加算し、WorkLogへ毎分複製しない。
タイマー0では自動停止しない。表示を0に留め、本人が継続している間の計測は続く。
これは自己申告の稼働時間であり、実際に集中していたことを検出した値ではない。
ブラウザー再読込・サーバー再起動でも時刻から復元。タブを閉じても継続する旨を
開始画面で短く伝え、終了後に記録を直せるようにする。離席の自動推測は初期対象外。

### MCPとブラウザーの操作境界

独立したREST APIは増やさず、現行のMCPと認証済みserver functionから同じサービスを呼ぶ。
すべての更新で現行のworkspace全体の `expectedRevision` と `requestId` を使用する。
秒ごとの表示は書き込みを発生させないので、時計によるrevision競合は生じない。

| 操作口                                             | 利用者 | 入出力・変更                                                              |
| -------------------------------------------------- | ------ | ------------------------------------------------------------------------- |
| publish_activities（拡張）                         | Dots   | timeEstimateを含む提案。今日の候補・計測は変えない                        |
| update_activity_progress（拡張）                   | Dots   | remainingMinutesを追加。既存reason/evidence必須。残りだけの変更も可       |
| update_activity（拡張）                            | 本人   | 時間overrideの設定・解除。既存状態変更と同じ扱い                          |
| get_activity_context（拡張）                       | 両方   | time、未終了セッション、serverNow。既存ページングを維持                   |
| get_day_plan / update_day_plan（新規）             | 両方   | date、IANA timeZone、候補の追加・除外・順序変更。更新はreasonを添える     |
| startFocus / changeFocus（新規server function）    | 本人   | activityIdまたはsessionId、操作と任意budget。receiptと現在のsessionを返す |
| saveWorkLog / deleteWorkLog（新規server function） | 本人   | IDで手入力・訂正・削除。AIの稼働時間を本人実績として書かせない            |

ブラウザーの操作名はserver functionのexport名に対応する。集中開始・実績改変はDots向けMCPへ公開しない。
Dotsには見積もり・自動分類・進捗を任せ、本人が押したときだけ集中を始める。
既存MCPの「本人の操作を保存するツール」を自律的な再見積もりには使わせない。

成功は既存のreceipt形式を維持。再送は同一requestId・同一入力を使い、同一receiptを返す。
入力を変更したら新しいrequestId。revision-conflict時は最新状態を読み直して再判断する。
既存の `{ ok: false, error: { code, message } }` とinvalid-input/idempotency-conflict等を維持し、
別セッションが未終了・終了済みセッションへの変更は新設 `state-conflict` とする。
残り0でもcompletedを暗黙に指定しない。終了・実績・Activity状態変更・receipt・イベントは
同じDBトランザクションで確定する。

Start here / If there’s roomはActivityのAI推奨区分に従って表示する。追加ごとの
人手トリアージや表示件数の上限を設けない。LaterとNot neededは本人が明示的に
選んだ場合だけ表示から外す。

### イベントとDotsへの指示

現在の公開イベントは `activity.created` / `activity.status_changed`。
時間変更まで既に配信されるとは扱わない。
新設する `activity.time_changed` はactivityId、origin、requestId、revision、
changedFields、occurredAtを持つ。クライアントは最新contextを取得する。
WorkLog確定/訂正と有効な時間値変更で発火し、秒ごとのカウントダウンでは送らない。
AI提案がowner overrideに隠れて有効値が不変なら配信しない。
日次候補の変更は初期実装ではブラウザーの更新通知だけに留める。

Dotsの指示は次の差分を追加する。

> 新規タスクには、本人が能動的に作業する時間を粗い分単位で見積もり、根拠とともに付ける。
> 会話待ち・AIの実行時間を含めない。本人に時間の入力や確認を毎回求めない。
> 進捗の根拠が増えたら残り時間を更新する。経過時間だけで完了としない。
> 本人の修正を尊重し、集中中のタスクや今日の候補を新着だけで入れ替えない。
> 自分の更新イベントへ反射的に再更新せず、新しい根拠がある場合だけ変更する。

手入力・既存タスクの未見積は、本人originのcreatedイベントまたは次回の明示的な
インボックス見直しでDotsが補う。履歴全件への強制バックフィルはしない。
タイマー開始の応答にAI推論を待たせない。
Homeの冒頭の案内文もAI推奨区分を参照する。

### 画面構成と実装箇所

```text
← 今日へ                         集中中

           日程調整の返信
      候補日を確認して返信案を整える

             ◯  14:32
            今回は15分

    残りの目安 約30分 · 続ければ16:10ごろ

        一時停止      ＋5分
        完了          今日はここまで

       返信案を開く    元メッセージ
```

Homeのカードには「約15分」と開始ボタン。全体見積もりと残りを同時に並べず、
着手後は残りの目安を優先する。HomeやBoardのFocus操作はSheetで集中画面を開く。
専用ルート `/focus/$activityId` は直接リンク・再開用にも残す。ルートを開くだけでは開始しない。
元メッセージは既存Sheet、返信案は既存編集・送信機能を再利用する。
送信と完了判定は既存方針を維持し、タイマー追加に伴って結合しない。
数字でも残り時間を伝え、色だけに依存しない。秒読みをスクリーンリーダーへ毎秒通知しない。

- `activities/model.ts`：見積もり・override・進捗入力・context出力。
- `activities/repository.server.ts`：見積もり更新、状態変更時の集中終了、既存receipt連携。
- `storage/schema.ts` とmigration：activity_time、focus_sessions、work_logs、day_selections。
- 新規 `features/focus/`：純粋な時間計算、永続化サービス、集中画面。
- `mcp/workspace-tools.server.ts`：説明と入力、context、日次候補の操作。
- `mcp-events/`：time_changedの購読schema、outbox、originフィルター。
- `activities/activity-card.tsx`、`home/execution-workbench.tsx`：目安・開始・日次選定。

スキーマ追加後も既存Activityはそのまま読める。新規テーブルは空から開始し、
既存inProgressを勝手にタイマーへ変換しない。ActivityはAI推奨sectionに応じて
Homeへ自動表示する。READMEには実装された機能・操作口を追記する。

### 受け入れ条件

1. Dotsが返信・雑用の両方に見積もりを付けられ、本人は入力・承認なしで開始できる。
2. ownerの見積もり編集はAI更新後も有効。解除すると最新AI値へ戻る。
3. AIがActivityを追加したら推奨sectionへ自動表示し、集中対象は勝手に開始しない。
4. 40分のタスクへ15分集中できる。15分終了だけではタスクも残り見積もりも完了しない。
5. 15分作業・15分休止・再開の例で、休止を実績に含めず完了見込みが15分後ろへ動く。
6. タイマー再読込、二重クリック、複数タブ、再送でも未終了セッションとWorkLogを重複作成しない。
7. 外部完了と本人の完了が競合しても、終了・実績確定は1回。後続要求は再読込で収束する。
8. 見積もり未取得やDots停止中も開始・休止・完了できる。架空のAI見積もりは表示しない。
9. 実績訂正と再見積もり後も二重減算しない。初回比較値は後から書き換わらない。
10. time_changedは更新1回につき1件、毎秒は0件。agent originは既存と同様に既定購読から除外。
11. AIが追加したActivityは自動分類され、Home表示前の手動選択を要求しない。
12. カレンダー導入時も時刻未指定の候補を残し、固定予定と仮の作業枠を区別する。

検証対象は純粋な時間計算、SQLiteトランザクション/競合、MCP公開schema、
主要操作と再読込のブラウザーテスト。カレンダーの受け入れ条件12は後続実装で検証する。
